---

`HEAD`와 사용자가 지정한 고정 기준점 사이의 diff를 두 축으로 리뷰합니다.

- **표준(Standards)**: 코드가 이 저장소에 문서화된 코딩 표준을 따르는가?
- **스펙(Spec)**: 코드가 원래 이슈·스펙을 충실히 구현하는가?

두 축은 서로의 컨텍스트를 오염시키지 않도록 **병렬 서브 에이전트**로 실행하고, 이 스킬이 결과를 모읍니다.

이슈 트래커는 이미 제공되어 있어야 합니다. `docs/agents/issue-tracker.md`가 없다면 사용자에게 `/setup-matt-pocock-skills`를 실행하라고 알려주세요.

## 절차

### 1. 고정 기준점 정하기

사용자가 말한 것이 고정 기준점입니다(커밋 SHA, 브랜치 이름, 태그, `main`, `HEAD~5` 등). 지정하지 않았다면 물어보세요.

diff 명령을 한 번 정해두세요: `git diff <fixed-point>...HEAD` (점 세 개. 머지 베이스와 비교합니다). 커밋 목록도 `git log <fixed-point>..HEAD --oneline`으로 적어두세요.

더 진행하기 전에 기준점이 해석되는지(`git rev-parse <fixed-point>`)와 diff가 비어 있지 않은지 확인하세요. 잘못된 참조나 빈 diff는 두 병렬 서브 에이전트 안이 아니라 여기서 실패해야 합니다.

### 2. 스펙 출처 찾기

원래 스펙을 다음 순서로 찾으세요.

1. 커밋 메시지의 이슈 참조(`#123`, `Closes #45`, GitLab `!67` 등). `docs/agents/issue-tracker.md`의 방식으로 가져옵니다.
2. 사용자가 인자로 넘긴 경로.
3. 브랜치 이름이나 기능과 일치하는 `docs/`, `specs/`, `.scratch/` 아래의 스펙 파일.
4. 아무것도 찾지 못하면 사용자에게 스펙이 어디 있는지 물으세요. 없다고 하면 **스펙** 서브 에이전트는 건너뛰고 "사용 가능한 스펙 없음"으로 보고합니다.

### 3. 표준 출처 찾기

저장소 안에서 코드 작성 방식을 문서화한 모든 것입니다. 예: `CODING_STANDARDS.md`, `CONTRIBUTING.md`.

저장소가 무엇을 문서화했든, 표준 축에는 항상 아래의 **냄새 기준(smell baseline)**이 함께 적용됩니다. 저장소가 아무것도 문서화하지 않았어도 적용되는 Fowler의 코드 냄새(_Refactoring_, 3장) 고정 목록입니다. 두 가지 규칙이 있습니다.

- **저장소가 우선합니다.** 문서화된 저장소 표준이 항상 이깁니다. 기준이 지적할 만한 것을 저장소 표준이 허용한다면 그 냄새는 지적하지 않습니다.
- **항상 판단의 문제입니다.** 각 냄새는 딱지가 붙은 휴리스틱("Feature Envy일 수 있음")이지 절대적인 위반이 아닙니다. 여기의 다른 표준과 마찬가지로, 도구가 이미 강제하는 것은 건너뛰세요.

각 냄새는 *무엇인지* → *어떻게 고치는지* 순서로 적혀 있습니다. diff와 대조해 보세요.

- **Mysterious Name(수수께끼 같은 이름)**: 이름만 봐서는 무엇을 하거나 담는지 알 수 없는 함수, 변수, 타입. → 이름을 바꾸세요. 정직한 이름이 떠오르지 않는다면 설계가 흐릿한 것입니다.
- **Duplicated Code(중복 코드)**: 같은 로직 형태가 변경 안의 여러 hunk나 파일에 나타남. → 공통 형태를 추출해 양쪽에서 호출하세요.
- **Feature Envy(기능 욕심)**: 자기 데이터보다 다른 객체의 데이터를 더 많이 건드리는 메서드. → 그 메서드를 탐내는 데이터 쪽으로 옮기세요.
- **Data Clumps(데이터 뭉치)**: 같은 몇 개의 필드나 매개변수가 계속 함께 다님(태어나고 싶어 하는 타입). → 하나의 타입으로 묶어서 넘기세요.
- **Primitive Obsession(기본형 집착)**: 자기 타입을 가질 만한 도메인 개념을 기본형이나 문자열이 대신함. → 그 개념에 작은 전용 타입을 주세요.
- **Repeated Switches(반복되는 switch)**: 같은 타입에 대한 같은 `switch`/`if` 연쇄가 변경 곳곳에 반복됨. → 다형성으로 바꾸거나, 두 곳이 공유하는 맵 하나로 바꾸세요.
- **Shotgun Surgery(산탄총 수술)**: 논리적 변경 하나 때문에 diff의 여러 파일을 흩어져 고쳐야 함. → 함께 바뀌는 것을 한 모듈로 모으세요.
- **Divergent Change(뒤엉킨 변경)**: 파일이나 모듈 하나가 서로 무관한 여러 이유로 수정됨. → 모듈마다 한 가지 이유로만 바뀌도록 나누세요.
- **Speculative Generality(추측성 일반화)**: 스펙에 없는 필요를 위해 추가된 추상화, 매개변수, 훅. → 지우세요. 실제 필요가 보일 때까지 다시 인라인하세요.
- **Message Chains(메시지 체인)**: 호출하는 쪽이 의존하면 안 되는 긴 `a.b().c().d()` 탐색. → 첫 객체의 메서드 하나 뒤로 그 탐색을 숨기세요.
- **Middle Man(중개자)**: 거의 위임만 하는 클래스나 함수. → 잘라내고 실제 대상을 직접 호출하세요.
- **Refused Bequest(거부된 유산)**: 상속받은 것 대부분을 무시하거나 덮어쓰는 하위 클래스나 구현체. → 상속을 버리고 합성을 쓰세요.

### 4. 두 서브 에이전트를 병렬로 실행하기

**표준 서브 에이전트 프롬프트**에는 다음을 넣으세요.

- 전체 diff 명령과 커밋 목록.
- 3단계에서 찾은 표준 출처 파일 목록과 **3단계의 냄새 기준 전문**(서브 에이전트는 그 외에는 접근할 방법이 없습니다).
- 지시: "관련된 파일/hunk마다 (a) diff가 문서화된 표준을 어기는 모든 곳을 표준(파일 + 규칙)을 인용해 보고하고, (b) 발견한 기준 냄새를 이름과 hunk 인용과 함께 보고하라. 절대적 위반과 판단의 문제를 구분하라. 문서화된 표준 위반은 절대적일 수 있지만 기준 냄새는 항상 판단의 문제이며, 문서화된 저장소 표준이 기준보다 우선한다. 도구가 강제하는 것은 건너뛰어라. 400단어 이내."

**스펙 서브 에이전트 프롬프트**에는 다음을 넣으세요.

- diff 명령과 커밋 목록.
- 스펙의 경로나 가져온 내용.
- 지시: "(a) 스펙이 요구했지만 빠졌거나 일부만 된 요구사항, (b) 요구하지 않았는데 diff에 들어간 동작(범위 초과), (c) 구현된 것처럼 보이지만 구현이 잘못된 것 같은 요구사항을 보고하라. 각 발견마다 스펙의 해당 줄을 인용하라. 400단어 이내."

스펙이 없으면 스펙 서브 에이전트를 건너뛰고 최종 보고서에 그 사실을 적으세요.

### 5. 모으기

두 보고서를 `## 표준 (Standards)`와 `## 스펙 (Spec)` 제목 아래에 그대로, 또는 가볍게 정리해서 보여주세요. 발견 사항을 합치거나 순위를 다시 매기지 **마세요**. 두 축은 의도적으로 분리되어 있습니다(_왜 두 축인가_ 참고).

마지막에 한 줄로 요약하세요. 축별 발견 개수와, _각 축 안에서_ 가장 심각한 문제(있다면)입니다. 축을 넘나들며 하나의 최악을 고르지 마세요. 그것이 바로 분리가 막으려는 순위 재조정입니다.

## 왜 두 축인가

변경은 한 축은 통과하고 다른 축은 실패할 수 있습니다.

- 모든 표준을 따르지만 엉뚱한 것을 구현한 코드 → **표준 통과, 스펙 실패.**
- 이슈가 요구한 것을 정확히 하지만 프로젝트 규칙을 어긴 코드 → **스펙 통과, 표준 실패.**

따로 보고해야 한 축이 다른 축을 가리지 않습니다.
