이 스킬은 현재 대화의 맥락과 코드베이스에 대한 이해를 바탕으로 스펙을 만듭니다. 사용자를 인터뷰하지 마세요. 이미 아는 것을 종합하기만 하세요.

이슈 트래커와 트리아지 라벨 어휘는 이미 제공되어 있어야 합니다. 없다면 사용자에게 `/setup-matt-pocock-skills`를 실행하라고 알려주세요.

## 절차

1. 아직 하지 않았다면 저장소를 탐색해 코드베이스의 현재 상태를 파악하세요. 스펙 전체에서 프로젝트 도메인 용어집의 어휘를 쓰고, 건드리는 영역의 ADR을 존중하세요.

2. 기능을 테스트할 경계(seam)를 스케치하세요. 새 경계보다 기존 경계를 우선하세요. 가능한 가장 높은 경계를 쓰세요. 새 경계가 필요하다면 가능한 가장 높은 지점에 제안하세요. 코드베이스 전체에 걸친 경계는 적을수록 좋고, 이상적인 개수는 하나입니다.

이 경계들이 사용자의 기대와 맞는지 확인하세요.

3. 아래 템플릿으로 스펙을 작성한 뒤 프로젝트 이슈 트래커에 게시하세요. 트리아지 라벨 `ready-for-agent`를 붙이세요. 별도의 트리아지는 필요 없습니다.

문제의 해결 방안을 사용자 관점에서 적습니다.

번호를 붙인 긴 사용자 스토리 목록입니다. 각 사용자 스토리는 다음 형식을 따릅니다.

## 구현 결정 (Implementation Decisions)

내려진 구현 결정 목록입니다. 다음을 포함할 수 있습니다.

- 새로 만들거나 수정할 모듈
- 수정될 모듈의 인터페이스
- 개발자가 밝힌 기술적 설명
- 아키텍처 결정
- 스키마 변경
- API 계약
- 구체적인 상호작용

구체적인 파일 경로나 코드 조각은 넣지 마세요. 금방 낡아버릴 수 있습니다.

예외: 프로토타입에서 나온 코드 조각이 문장보다 결정을 더 정확하게 담고 있다면(상태 머신, 리듀서, 스키마, 타입 형태) 관련 결정 안에 넣고 프로토타입에서 왔다고 짧게 적으세요. 동작하는 데모가 아니라 결정이 담긴 핵심 부분만 남기세요.

## 테스트 결정 (Testing Decisions)

내려진 테스트 결정 목록입니다. 다음을 포함하세요.

- 좋은 테스트의 기준(구현 세부가 아니라 외부 동작만 테스트)
- 테스트할 모듈
- 테스트의 기존 사례(코드베이스 안의 비슷한 테스트)
