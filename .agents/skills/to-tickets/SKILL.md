# 티켓으로 쪼개기

계획, 스펙, 대화를 **티켓** 묶음으로 쪼개세요. 각 티켓은 트레이서 불릿 방식의 수직 조각이며, 자신을 **차단(block)**하는 티켓을 밝힙니다.

이슈 트래커와 트리아지 라벨 어휘는 이미 제공되어 있어야 합니다. 없다면 사용자에게 `/setup-matt-pocock-skills`를 실행하라고 알려주세요.

## 절차

### 1. 맥락 모으기

대화 맥락에 이미 있는 것에서 출발하세요. 사용자가 인자로 참조(스펙 경로, 이슈 번호나 URL)를 넘기면 가져와서 본문과 댓글 전체를 읽으세요.

### 2. 코드베이스 탐색하기 (선택)

아직 하지 않았다면 코드베이스를 탐색해 현재 상태를 파악하세요. 티켓 제목과 설명에는 프로젝트 도메인 용어집의 어휘를 쓰고, 건드리는 영역의 ADR을 존중하세요.

구현을 쉽게 만들기 위해 코드를 미리 리팩터링(prefactor)할 기회를 찾으세요. "변경을 쉽게 만든 다음, 쉬운 변경을 하라."

### 3. 수직 조각 초안 잡기

작업을 **트레이서 불릿** 티켓으로 쪼개세요.

<vertical-slice-rules>

- 각 조각은 모든 계층(스키마, API, UI, 테스트)을 관통하는 좁지만 완전한 경로를 자릅니다. 한 계층만 가로로 자르는 것이 아니라 수직으로 자릅니다
- 완성된 조각은 그 자체로 시연하거나 검증할 수 있습니다
- 각 조각은 새 컨텍스트 창 하나에 들어갈 크기입니다
- 미리 하는 리팩터링은 가장 먼저 합니다

</vertical-slice-rules>

각 티켓에 **차단 관계(blocking edge)**를 정하세요. 즉 그 티켓을 시작하기 전에 끝나야 하는 다른 티켓들입니다. 차단하는 티켓이 없으면 바로 시작할 수 있습니다.

**넓은 리팩터링은 수직 조각의 예외입니다.** **넓은 리팩터링**이란 기계적인 변경 하나(컬럼 이름 바꾸기, 공유 심볼의 타입 바꾸기)의 **폭발 반경(blast radius)**이 코드베이스 전체로 퍼져서, 한 번의 수정으로 수천 개의 호출 지점이 동시에 깨지고 어떤 수직 조각도 초록 상태로 들어갈 수 없는 경우입니다. 억지로 트레이서 불릿에 끼워 넣지 말고 **확장–수축(expand–contract)** 순서로 진행하세요. 먼저 확장: 옛 형태 옆에 새 형태를 추가해 아무것도 깨지지 않게 합니다. 다음으로 호출 지점을 폭발 반경에 맞춘 묶음(패키지별, 디렉터리별)으로 옮기며, 각 묶음은 확장 티켓에 차단되는 별도 티켓입니다. 옛 형태가 아직 있으므로 묶음마다 CI가 초록으로 유지됩니다. 마지막으로 수축: 호출하는 곳이 하나도 남지 않으면 옛 형태를 지우며, 이 티켓은 모든 이전 묶음에 차단됩니다. 묶음조차 혼자서는 초록을 유지할 수 없다면 순서는 그대로 두되, 묶음들이 하나의 통합 브랜치를 공유하고 모두가 마지막 통합·검증 티켓을 차단하게 하세요. 초록은 그 티켓에서만 보장됩니다.

### 4. 사용자에게 확인받기

제안한 분할을 번호 목록으로 보여주세요. 티켓마다 다음을 보여주세요.

- **제목**: 짧고 설명적인 이름
- **Blocked by**: 먼저 끝나야 하는 다른 티켓(있다면)
- **제공하는 것**: 이 티켓이 동작하게 만드는 처음부터 끝까지의 동작

사용자에게 물으세요.

- 세분화 정도가 적절한가요? (너무 굵다 / 너무 잘다)
- 차단 관계가 맞나요? 각 티켓이 정말로 자신을 가로막는 티켓에만 의존하나요?
- 합치거나 더 쪼개야 할 티켓이 있나요?

사용자가 분할을 승인할 때까지 반복하세요.

### 5. 설정된 트래커에 티켓 게시하기

승인된 티켓을 게시하세요. **방법**은 `/setup-matt-pocock-skills`가 설정한 트래커에 따라 다릅니다. 어느 쪽이든 티켓 내용은 같고, 차단 관계를 표현하는 모양만 달라집니다.

- **로컬 파일** → 티켓마다 파일 하나를 `.scratch/<feature-slug>/issues/<NN>-<slug>.md`에 쓰고, 의존 순서대로(차단하는 티켓 먼저) `01`부터 번호를 매깁니다. 각 파일의 "Blocked by"에는 의존하는 티켓의 번호와 제목을 적습니다. 아래의 티켓별 파일 템플릿을 쓰세요. 파일 하나에 티켓 하나이며, 절대 한 파일로 합치지 않습니다.
- **실제 이슈 트래커(GitHub, Linear 등)** → 의존 순서대로(차단하는 티켓 먼저) 티켓마다 이슈 하나를 게시해, 각 티켓의 차단 관계가 실제 식별자를 참조할 수 있게 합니다. 플랫폼에 기본 차단 / 하위 이슈 관계가 있으면 그것을 쓰고, 없으면 각 티켓의 "Blocked by"에 차단하는 이슈를 적습니다. 별도 지시가 없으면 트리아지 라벨 `ready-for-agent`를 붙입니다. 티켓은 애초에 에이전트가 가져가 처리할 수 있게 만들어졌기 때문입니다.

**최전선(frontier)**부터 처리하세요. 차단하는 티켓이 모두 끝난 티켓입니다. 순전히 일렬로 이어진 사슬이라면 위에서 아래로 진행하면 됩니다.

상위 이슈를 닫거나 수정하지 마세요.
