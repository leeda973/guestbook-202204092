# 도메인 모델링

설계하면서 프로젝트의 도메인 모델을 적극적으로 만들고 다듬으세요. 이것은 *능동적인* 규율입니다. 용어에 이의를 제기하고, 경계 상황 시나리오를 만들어 내고, 용어집과 결정이 굳어지는 순간 바로 기록합니다. (어휘를 확인하려고 `CONTEXT.md`를 *읽기만* 하는 것은 이 스킬이 아닙니다. 그건 어떤 스킬이든 할 수 있는 한 줄짜리 습관입니다. 이 스킬은 모델을 소비할 때가 아니라 바꿀 때 쓰는 것입니다.)

## 파일 구조

대부분의 저장소는 컨텍스트가 하나입니다.

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

루트에 `CONTEXT-MAP.md`가 있으면 컨텍스트가 여러 개인 저장소입니다. 맵이 각 컨텍스트의 위치를 알려줍니다.

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 시스템 전체 결정
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 컨텍스트별 결정
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

파일은 필요할 때 만드세요. 쓸 내용이 생겼을 때만 만듭니다. `CONTEXT.md`가 없으면 첫 용어가 정해질 때 만들고, `docs/adr/`가 없으면 첫 ADR이 필요할 때 만드세요.

## 세션 중에 할 일

### 용어집과 대조해 이의를 제기하세요

사용자가 `CONTEXT.md`의 기존 용어와 충돌하는 말을 쓰면 즉시 짚으세요. "용어집에서는 '취소'를 X로 정의하는데, 지금은 Y라는 뜻으로 쓰시는 것 같아요. 어느 쪽인가요?"

### 모호한 말을 날카롭게 다듬으세요

사용자가 모호하거나 여러 뜻으로 쓰이는 말을 쓰면, 정확한 표준 용어를 제안하세요. "'계정'이라고 하셨는데, Customer를 말씀하시는 건가요, User를 말씀하시는 건가요? 둘은 다른 개념이에요."

### 구체적인 시나리오로 따져보세요

도메인 관계를 논의할 때는 구체적인 시나리오로 검증하세요. 경계 상황을 찌르는 시나리오를 만들어서, 개념 사이의 경계를 사용자가 정확히 정하도록 만드세요.

### 코드와 교차 확인하세요

사용자가 무언가가 어떻게 동작한다고 말하면 코드도 그런지 확인하세요. 모순을 찾으면 드러내세요. "코드는 Order 전체를 취소하는데, 방금 부분 취소가 가능하다고 하셨어요. 어느 쪽이 맞나요?"

### CONTEXT.md를 그 자리에서 갱신하세요

용어가 정해지면 바로 그 자리에서 `CONTEXT.md`를 갱신하세요. 모아두지 말고 생길 때마다 기록하세요. 형식은 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)를 따르세요.

`CONTEXT.md`에는 구현 세부 사항이 전혀 없어야 합니다. `CONTEXT.md`를 스펙이나 메모장, 구현 결정 보관소로 쓰지 마세요. 용어집일 뿐 그 이상도 이하도 아닙니다.

### ADR은 아껴서 제안하세요

다음 세 가지가 모두 참일 때만 ADR 작성을 제안하세요.

1. **되돌리기 어렵다**: 나중에 마음을 바꾸는 비용이 크다
2. **맥락 없이는 놀랍다**: 미래의 독자가 "왜 이렇게 했지?"라고 궁금해할 것이다
3. **실제 트레이드오프의 결과다**: 진짜 대안이 있었고 구체적인 이유로 하나를 골랐다

하나라도 빠지면 ADR을 건너뛰세요. 형식은 [ADR-FORMAT.md](./ADR-FORMAT.md)를 따르세요.
