# ADR 형식

ADR은 `docs/adr/`에 두고 순차 번호를 씁니다: `0001-slug.md`, `0002-slug.md` 등.

`docs/adr/` 디렉터리는 첫 ADR이 필요할 때 만드세요.

## 템플릿

```md
# {결정의 짧은 제목}

{1~3문장: 어떤 맥락이었고, 무엇을 결정했고, 왜 그랬는지.}
```

이게 전부입니다. ADR은 한 문단이어도 됩니다. 가치는 섹션을 채우는 데 있지 않고, 결정이 *내려졌다는 사실*과 *그 이유*를 기록하는 데 있습니다.

## 선택 섹션

정말 가치를 더할 때만 넣으세요. 대부분의 ADR에는 필요 없습니다.

- **Status** 프런트매터(`proposed | accepted | deprecated | superseded by ADR-NNNN`): 결정을 다시 검토할 때 유용합니다
- **Considered Options**: 기각한 대안을 기억할 가치가 있을 때만
- **Consequences**: 뻔하지 않은 파급 효과를 짚어야 할 때만

## 번호 매기기

`docs/adr/`에서 가장 큰 번호를 찾아 1을 더하세요.

## ADR을 제안할 때

다음 세 가지가 모두 참이어야 합니다.

1. **되돌리기 어렵다**: 나중에 마음을 바꾸는 비용이 크다
2. **맥락 없이는 놀랍다**: 미래의 독자가 코드를 보고 "대체 왜 이렇게 했지?"라고 궁금해할 것이다
3. **실제 트레이드오프의 결과다**: 진짜 대안이 있었고 구체적인 이유로 하나를 골랐다

쉽게 되돌릴 수 있는 결정이면 건너뛰세요. 그냥 되돌리면 됩니다. 놀랍지 않은 결정이면 아무도 이유를 궁금해하지 않습니다. 진짜 대안이 없었다면 "당연한 것을 했다" 외에 기록할 것이 없습니다.

### 해당하는 것

- **아키텍처의 형태.** "모노레포를 쓴다." "쓰기 모델은 이벤트 소싱이고, 읽기 모델은 Postgres로 투영한다."
- **컨텍스트 간 통합 패턴.** "Ordering과 Billing은 동기 HTTP가 아니라 도메인 이벤트로 통신한다."
- **종속성이 생기는 기술 선택.** 데이터베이스, 메시지 버스, 인증 제공자, 배포 대상. 모든 라이브러리가 아니라, 교체하는 데 분기 하나가 걸릴 만한 것만.
- **경계와 범위 결정.** "Customer 데이터는 Customer 컨텍스트가 소유하고, 다른 컨텍스트는 ID로만 참조한다." 명시적인 "안 한다"도 "한다"만큼 가치 있습니다.
- **당연한 길에서 의도적으로 벗어난 것.** "X 때문에 ORM 대신 SQL을 직접 쓴다." 합리적인 독자라면 반대로 가정할 만한 모든 것. 다음 엔지니어가 의도된 것을 "고치지" 않게 막아줍니다.
- **코드에 드러나지 않는 제약.** "컴플라이언스 요건 때문에 AWS를 쓸 수 없다." "파트너 API 계약 때문에 응답 시간은 200ms 미만이어야 한다."
- **기각 이유가 뻔하지 않은 대안.** GraphQL을 검토하고 미묘한 이유로 REST를 골랐다면 기록하세요. 그렇지 않으면 여섯 달 뒤 누군가 GraphQL을 다시 제안합니다.
