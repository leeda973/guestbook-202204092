# 테스트 주도 개발

TDD는 빨강 → 초록 루프입니다. 이 스킬은 그 루프가 남길 가치가 있는 테스트를 만들도록 돕는 참고 자료입니다. 좋은 테스트란 무엇인지, 테스트를 어디에 두는지, 안티패턴, 루프의 규칙을 다룹니다. 모든 섹션이 매 사이클에 적용됩니다. 루프가 끝난 뒤가 아니라 시작 전과 진행 중에 참고하세요.

코드베이스를 탐색할 때는 `CONTEXT.md`(있다면)를 읽어 테스트 이름과 인터페이스 어휘가 프로젝트의 도메인 언어와 맞도록 하고, 건드리는 영역의 ADR을 존중하세요.

## 좋은 테스트란

테스트는 구현 세부가 아니라 공개 인터페이스를 통해 동작을 검증합니다. 코드는 완전히 바뀔 수 있어도 테스트는 바뀌지 않아야 합니다. 좋은 테스트는 명세처럼 읽힙니다. "유효한 장바구니로 결제할 수 있다"는 어떤 기능이 있는지 정확히 알려주며, 내부 구조에 신경 쓰지 않으므로 리팩터링에도 살아남습니다.

예시는 [tests.md](tests.md), 모킹 지침은 [mocking.md](mocking.md)를 보세요.

## 경계(Seam): 테스트를 두는 곳

**경계(seam)**는 테스트하는 공개 경계입니다. 안을 들여다보지 않고 동작을 관찰할 수 있는 인터페이스입니다. 테스트는 경계에 두고, 절대 내부를 대상으로 하지 않습니다.

**미리 합의한 경계에서만 테스트하세요.** 테스트를 쓰기 전에 테스트할 경계를 적고 사용자에게 확인받으세요. 확인받지 않은 경계에는 어떤 테스트도 쓰지 않습니다. 모든 것을 테스트할 수는 없으므로, 경계를 미리 합의해야 테스트 노력이 모든 경계 상황이 아니라 핵심 경로와 복잡한 로직에 집중됩니다.

물어보세요: "공개 인터페이스는 무엇이고, 어느 경계를 테스트해야 하나요?"

그 인터페이스의 모양 자체가 문제일 때(모듈이 얼마나 깊은지, 경계를 어디에 둬야 하는지, 인터페이스가 무엇을 노출해야 하는지)는 Skill 도구로 "codebase-design"을 호출해 어휘를 참고하세요. 모듈, 인터페이스, 깊이, 경계, 어댑터, 레버리지, 지역성 용어의 공통 출처이며, 세션으로 진행하는 것이 아니라 참고하는 자료입니다.

## 안티패턴

- **구현 결합(Implementation-coupled)**: 내부 협력 객체를 모킹하거나, private 메서드를 테스트하거나, 옆길로 검증합니다(인터페이스를 쓰는 대신 데이터베이스를 직접 조회). 징후: 동작은 그대로인데 리팩터링하면 테스트가 깨집니다.
- **동어반복(Tautological)**: 단언이 기대값을 코드와 같은 방식으로 다시 계산합니다(`expect(add(a, b)).toBe(a + b)`, 같은 방식으로 손으로 만든 스냅샷, 자기 자신과 같다고 단언하는 상수). 그래서 구조상 항상 통과하고 코드와 절대 어긋날 수 없습니다. 기대값은 독립적인 진실의 원천에서 와야 합니다. 검증된 리터럴, 직접 계산한 예시, 스펙 등입니다.
- **수평 분할(Horizontal slicing)**: 테스트를 전부 먼저 쓰고 구현을 전부 나중에 합니다. 한꺼번에 쓴 테스트는 _상상한_ 동작을 검증합니다. 사용자에게 보이는 동작이 아니라 사물의 _모양_을 테스트하게 되고, 테스트가 실제 변경에 둔감해지며, 구현을 이해하기도 전에 테스트 구조에 묶이게 됩니다. 대신 **수직 조각**으로 일하세요. 테스트 하나 → 구현 하나 → 반복이며, 각 테스트는 지난 사이클에서 배운 것에 반응하는 **트레이서 불릿**입니다.

## 루프의 규칙

- **초록 전에 빨강.** 실패하는 테스트를 먼저 쓰고, 그것을 통과시킬 만큼만 코드를 쓰세요. 앞으로의 테스트를 예상하거나 추측성 기능을 넣지 마세요.
- **한 번에 한 조각.** 사이클마다 경계 하나, 테스트 하나, 최소 구현 하나입니다.
- **리팩터링은 루프에 속하지 않습니다.** 리팩터링은 빨강 → 초록 구현 사이클이 아니라 리뷰 단계(`code-review` 스킬 참고)에 속합니다.
